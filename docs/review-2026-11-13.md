## Findings in priority order

### High: mixed-cart quantities need verified filtering

Follow-up implementation after client/manager confirmation: filtering is now built
locally, with 18 physical selection/inspection tests. It requires real product-ID
configuration before deployment; actual wire shape/IDs are still unavailable.
See bump-offer-diagnosis.md. The paragraphs below describe the reviewed defect.

Source: app/DTOs/OrderData.php:69. Every supplied item quantity counts as another
copy of the configured static book. A book + digital-copy bump with quantity one
each becomes two printed copies IF both are sent in items. October screenshots
showed a mixed checkout, but its actual webhook wire payload was not verified.
This is a confirmed parser limitation, not evidence that a real overprint occurred.

Current Phase 1 contract requires book-only items or an explicit physical-book
quantity. Next owner action: verify a redacted paid-order payload, the GHL workflow
mapping and physical/digital product identifiers. Add product selection with tests
if full carts must be accepted. Do not guess product identity from price/name alone.

### Medium: repeat buyers share one GHL field pair

Source: app/Services/GhlApiService.php:98. All orders for a Contact write the same
Lulu Status and Lulu Job ID. An older pending recovery can overwrite a newer
purchase's Contact summary. Two sequential PUTs can also temporarily leave status
and job ID from different attempts if the second request fails. Per-order local
history remains correct; the pair is not an order-level history in GHL.

Not changed in this review: the intended repeat-purchase display/notification
policy has not been specified. Define whether this is a latest-order summary or
requires per-order records before altering synchronization semantics.

### Medium: payment eligibility depends on the approved GHL workflow

Source: app/DTOs/OrderData.php:50. Missing payment status defaults to paid and
known explicit unpaid states are rejected. The app does not verify Stripe or
authenticate the event type as a payment event. A misconfigured workflow can send
an unpaid checkout into fulfillment. This trust boundary is documented, not a new
gateway-verification feature request. Verify the actual paid-order trigger/filter.

### Medium: serialized order JSON is unsupported

Source: app/DTOs/OrderData.php:35. GHL custom data may render order JSON as text in
its editor. The DTO expects structured arrays, not a JSON-encoded order string.
An isolated check rejects string order/payload envelopes with InvalidArgumentException,
which the controller maps to 422. No current saved wire payload confirms this
happens in production. Inspect the wire shape before extending normalization;
add regression coverage if serialized-envelope support is required.

### Medium: manual sync and field-change notifications need operational control

Source: bootstrap/app.php scheduler lock and app/Console/Commands/SyncLuluStatus.php.
withoutOverlapping applies to scheduler launches; manual sync invocations have no
shared command lock with it. --ghl-only intentionally replays saved pending states,
which may be older than the remote job state. Overlapping execution can produce
duplicate/out-of-order GHL writes and associated workflow notifications. Current
runbook says use one recovery at a time and avoid overlap. No concurrency/load
verification was performed. Consider shared locking if concurrent operation is needed.

## Fixed in this review

Source: app/Models/Order.php:69. DELIVERED previously fell through to
print_job_created, causing a completed job to look active and be polled repeatedly.
DELIVERED now maps to existing local shipped, preserving raw DELIVERED for the
timeline and GHL. No enum/schema/UI theme change. Normal full polling repairs
eligible old records; --ghl-only intentionally does not change local fulfillment.
Do not run full polling just as a code test: it writes GHL and can recover emails.

A regression test exercises a previously misclassified delivered order, confirms
raw status and no-retry behavior, and confirms no second poll once fully synced
with both initial email markers. This fix still requires production deployment.
